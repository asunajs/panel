# 从 0.3.x 面板迁移到 0.4

给**用着老面板（0.3.x，QuickJS 版）**的人：这份指南把旧数据搬进 0.4，让插件账号、
任务计划、脚本、运行历史无缝接上。三条纪律与实现见 `src/migrate.rs`：
默认只预览、落库前自动快照、可重复跑（**不覆盖你已有的东西**）。

## 一句话

```bash
PANEL_DATA_DIR=<0.4 的数据目录> ./panel migrate <旧数据目录> --apply \
  --with-tasks --with-runs-history --with-notify --with-plugin-data
```

不给来源路径会**自动扫描**常见位置（`~/Library/Application Support/plugin-panel`
这类布局都认），扫到多个会按可信度排序让你挑。也可以走界面：**设置 → 从 0.3.x
面板迁移**（扫描 → 预览 → 勾选项 → 迁移），效果与 CLI 相同。

## 搬什么（矩阵）

| 旧数据 | 0.4 去向 | 开关 | 说明 |
|---|---|---|---|
| state 表（插件键值：账号、计划、袋子…） | 0.4 的 state 表（同结构） | 总是 | mcloud 家族的全部键值；孤儿袋默认不搬 |
| mcloud_runs（插件自己的运行历史） | 0.4 的 mcloud_runs 表 | 总是 | 按 (task, 计划, 触发) 去重 |
| **jobs 表的任务**（含用户改过的计划、暂停、预算、提前量、摘要） | 0.4 的 tasks 表 | `--with-tasks` | 生效计划 = 用户覆盖值优先；`suggest_cron` 记插件原始计划；暂停的迁过来还是暂停 |
| **`__script__` 脚本任务**（文件 + 计划） | 0.4 的脚本（`data/scripts/` + scripts 表） | `--with-tasks` | 脚本文件不在的只报不搬 |
| 老面板 runs 表（运行历史 770 行那种） | 0.4 的运行记录页 | `--with-runs-history` | 本地时间串 → 毫秒；ok → status；按 (plugin, task, started_at) 去重 |
| push_config（通知渠道，如 Server酱 SendKey） | config.json 的 `notify.channels` | `--with-notify` | **渠道默认停用**（老推送多半也是关的）；开渠道、配推送规则在界面里做 |
| plugin-data/<插件>/（各插件配置文件） | 0.4 的 plugin-data/ | `--with-plugin-data` | 整目录拷贝，只增不删 |
| scripts/ 目录（旧散脚本文件） | 0.4 的 scripts/ | `--with-scripts` | 只增不删 |
| auth.json（旧令牌） | 0.4 的 auth.json | `--adopt-token` | **目标已有凭据就不覆盖**；两边是同一格式（盐 + PBKDF2） |
| logs（旧 jsonl 日志文件） | 不迁 | — | 0.4 的日志在库里且按运行归属；旧文件留在原地可翻 |
| 旧插件 .js 文件 | 不迁 | — | 0.3 的插件跑在 0.4 上契约不同——装各插件的 **0.4 版**（见下） |

## 任务怎么「平滑接管」

0.4 的插件加载后会注册自己的任务；调度器发现数据库里已有同名任务行，就把
**你改过的状态原样接管**：暂停保持暂停、你覆盖的计划保持你的计划、提前量和
摘要都在。没装 0.4 版的插件，它们的任务先以**占位**形式列在任务页（懒加载，
不会误触发），装上 0.4 版、重启面板后自动接管。预览会明确告诉你哪些插件
已有 0.4 版、哪些还没有。

## 步骤

1. **停旧面板**（同一个库两个写者容易撞），确认旧数据目录里有 `panel.db`。
2. **装好 0.4 面板**（`cargo build --release` 或现成二进制），能正常启动。
3. **预览**（只读，不写任何东西）：

   ```bash
   PANEL_DATA_DIR=<0.4 数据目录> ./panel migrate <旧数据目录>
   ```

   核对：任务条数、脚本任务、渠道、运行历史行数；「还没有 0.4 版的插件」
   清单会列出来（先去装它们的 0.4 版也行，装完再迁）。
4. **应用**（写前自动做 `panel.db.premigrate-<时间戳>` 快照）：

   ```bash
   PANEL_DATA_DIR=<0.4 数据目录> ./panel migrate <旧数据目录> --apply \
     --with-tasks --with-runs-history --with-notify --with-plugin-data
   ```

5. **重启 0.4 面板**。插件重新读状态；插件页刷新即可看到账号与历史。
6. **收尾**：任务页确认各任务的计划与暂停状态；通知渠道是停用状态，
   开关与推送规则在 设置 → 通知 里配。

## 界面操作

设置页底部有「从 0.3.x 面板迁移」卡片：扫描（可手填路径）→ 每个候选显示
键数 / 任务数 / 账号数 / 运行历史行数 → 预览摊出明细 → 勾选迁移内容 →
迁移。结果与 CLI 完全同一份实现（`crate::migrate`），写前同样自动快照。

## 没搬的东西（为什么）

- **旧插件 .js**：0.3 插件跑不了 0.4（引擎与契约都换了）——各插件的 0.4 版
  由各自的插件项目提供（mcloud / mgmusic 都有；没有的去插件项目要）。
- **旧日志（jsonl 文件）**：0.4 的日志在库里、按运行归属；旧文件留在原地。
- **令牌**：默认不接管（换面板是重新设口令的机会）；要接用 `--adopt-token`
  （目标已有凭据时不覆盖）。
- **push_outbox / 发送记录**：一次性的推送结果，没有跨面板的价值。

## 重复跑会怎样

「可重复跑」= 幂等，**不是**用旧值盖新值。所以第二次跑时：

- 插件键值（state）按 key 覆盖 —— 旧库是唯一来源，这是它的本职；
- **任务不覆盖**：0.4 里已有同名任务就原样保留（你在 0.4 里改过的计划/暂停/预算不会被回滚），
  结果里报「N 条任务目标里已有、保留你现在的设置」；
- **脚本文件不覆盖**：目标里已有同名文件就跳过，报「N 个脚本文件目标里已有、没覆盖」；
- 运行历史按 (plugin, task, started_at) 去重，已有的不再插。

想强制用旧值盖掉，先手动删掉目标里那条任务/文件再迁。

## 文件名校验

0.4 的脚本名只允许字母、数字、`-` `_` `.`。0.3 允许「每日签到.py」「my script.py」这种名字，
这类**不会搬**（否则会留下「列表里看得到、点开报非法脚本名」的死记录），结果里报
「N 个脚本文件名不合 0.4 规则没搬，请改名后再迁」。

## 扫描不会认错自己

自动发现用的是**反向判据**：库里有 0.4 独有的表（`plugins` / `notify_outbox`）就不是 0.3。
早先只看「有没有 state 表」，而 0.4 的 state 表是插件加载时自己建的 —— 于是把当前面板
（以及线上实例）自己的数据目录列成「0.3 旧面板」，启动提示会指着用户自己的库喊「来迁移」。

迁移成功后标记写在 `<数据目录>/migrate-0.3.json`，同一个旧库不再重复提醒；
「不再提醒」按钮写的是同一个文件的 `dismissed`。

## 迁移中的坑（为什么这么设计）

- **0.3 的脚本任务文件在 `<旧数据目录>/tasks/` 下**（`py/hello.py` 这种相对路径），
  目录没了 = 文件没了：这类只报不搬，免得迁出一堆「文件缺失」的死记录。
- **jobs 表的 `schedule` 是插件建议、`override_expr` 是你的覆盖**：迁移把覆盖值
  当生效计划（cron），原始建议记进 `suggest_cron` ——「恢复默认」恢复的才是对的。
- **未装插件的占位任务**：显示为懒加载占位、不会误触发；不想要就在任务页删除。
- **通知渠道默认停用**：0.3 的推送总开关多半也是关的；渠道配置（SendKey 等）
  原样搬，启用与推送规则由你决定。
