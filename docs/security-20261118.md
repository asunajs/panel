# 红队演练：恶意插件与恶意脚本（2026-11-18）

授权范围内对**探针实例**（18997，合成凭据）的黑盒测试：实现恶意插件与恶意脚本，
目标是「拿到面板登录态、或其他插件的数据、并外传给恶意服务器」。面板代码零改动
——纯黑盒，从插件 / 脚本 / 自带界面三个面攻击。恶意服务器只绑本机 / 局域网
（`192.168.3.196:8899` 收集端 + `127.0.0.1:8898` 回环对照），全程合成凭据。

结论先行：**10 个向量 8 个成功**。最大的洞不是引擎逃逸，而是两个「设计时认为是
便利」的决定：**全体插件共享一个 SQLite**（V1/V7 直接读走别的插件的全部数据）
和**插件界面与面板同源**（V9 借浏览器会话读一切 API）。令牌本身防得很好。

## 向量 × 结果矩阵

| # | 向量 | 结果 | 证据（摘录） |
|---|---|---|---|
| V1 | **共享 SQLite 跨插件读**：`host.sqlite_query("SELECT … FROM state")` —— 其他插件的全部键值都在这张表 | ✅ 成功 | evil 的 api/dump 返回 `victim.config = {"token":"SCT-victim-合成令牌","accounts":[…]}` |
| V2 | **auth.json 外传**（盐 + PBKDF2 哈希 → 弱口令可离线爆破） | ✅ 成功（脚本 = 普通进程，node:fs 直读）。**设计边界**：脚本=你的用户权限，见 P2 | 恶意服务器收到 `{"algo":"pbkdf2-hmac-sha256","hash":"d89d49…","salt":"0075973c…","iter":10000}`。⚠ 读数口径：探针跑的是 **debug 构建（10k 迭代）**；真实部署 release 是 **210k** —— GPU 单卡对 8 位小写+数字要数天、字典对人类口令分钟级，纯暴力不可行。210k 仍低于 OWASP 基线（PBKDF2-SHA256 建议 600k），建议上调（auth.json 记录迭代数，跨版本兼容已支持） |
| V3 | **脚本无围栏**：回环恶意服务器直连 | ✅ 成功（脚本=普通进程，无 SSRF 门——设计边界，见 P2） | `POST /V3-script-loopback-ok`（引擎侧被门拦，脚本侧畅通无阻） |
| V4 | **SSRF 门 DNS 盲区**：`localtest.me`（公网域名 → 127.0.0.1）过门 | ✅ 成功 | 引擎 fetch `http://localtest.me:8787/readyz` → 200 全状态（门只做字符串匹配，不做 DNS 解析——ssrf.rs 注释承认是刻意的） |
| V5 | 回环恶意服务器直连（对照） | ✅ 被门拦 | 引擎 fetch 127.0.0.1 → 「出站目标被 SSRF 防护拒绝」（但 V4 的域名绕过使其失效） |
| V6 | **process 模块：全量环境变量外传** | ✅ 成功 | `import('process').env` 全量 POST 到恶意服务器——含面板进程继承的**一切敏感值** |
| V7 | **ATTACH DATABASE 任意 sqlite 文件读 + 写** | ✅ 成功 | `ATTACH '/tmp/redteam/evil-target.db'` → 读 secrets 表 + 写入 `evil-was-here`（任意路径建/写 sqlite 文件 = 文件写原语） |
| V8 | 跨插件 globalThis 隔离 | ✅ 防御在位 | evil 留标记 → victim runtime 不可见（一插件一 runtime） |
| V9 | **同源会话读其他插件 API**：插件自带界面与面板同源，浏览器自动带会话 cookie | ✅ 成功 | 会话票 `GET /plugins/victim/api/config` → 受害者账号配置原样返回 |
| V10 | **process.exit DoS**：插件一行杀死整个面板进程 | ✅ 成功 | 面板进程退出（launchd 会拉起，但中断真实） |

**没拿到的东西**（防御在位）：`PANEL_TOKEN` 明文（启动即从环境删除，auth.rs 头注）；
localStorage 令牌（新版会话流不落 localStorage——恶意界面的扫描只回 theme 键）；
跨插件 JS 全局（V8）；对回环的引擎直连（V5，被门拦——但被 V4 的域名绕过架空）。

## 根因与缓解（按优先级）

### P0-1 共享 SQLite 无隔离（V1 / V7）

全体插件共享一个 `panel.db` 一个连接：`sqlite_query("… FROM state")` 一句话读走
所有插件的键值（真实部署里 = mcloud 的账号 cookie、mgmusic 的设备令牌）。
`ATTACH DATABASE` 更进一步 = **任意路径的 sqlite 文件读 + 建文件写**。

缓解（按成本递增）：

1. **挡 ATTACH**（一行）：DB actor 建连后
   `conn.set_limit(rusqlite::limits::Limit::Attached, 0)` —— V7 的文件写原语立即消失；
2. **state 表行级隔离**：键强制 `<插件名>.` 前缀（读时 WHERE 前缀过滤）——挡 V1 的
   跨插件读，mcloud 家族键名天然合规；
3. **长期：每插件独立 db 文件**（`plugin-data/<name>/db.sqlite`）——隔离最彻底，
   迁移成本高，需要一轮设计。

### P0-2 process.exit = 一行杀面板（V10）

LLRT 的 process 模块把 `exit` 暴露给了插件。一行 `process.exit(1)` 杀掉整个面板
进程（launchd 会拉起，但已是一次真实中断）。缓解：引擎组装时摘除 `process.exit`
（保留 `env` 是否暴露另议，见 P1-1），或至少 `kill_on_drop` 语义面板化。

### P1-1 process.env 全量暴露（V6 / V9）

面板进程的环境变量被插件全量读到——本次演练里连**面板宿主环境的 agent 凭据**
（ZCODE_* 系）都在里面。缓解：引擎给插件的环境改为**白名单注入**
（`PANEL_SCRIPT_DATA` / `PANEL_BIND` 等面板自有变量），宿主环境不透传；
`process.exit` 同步摘除。

### P1-2 插件界面与面板同源（V9）

插件自带界面跑在与面板**同一个 origin**（`/plugins/<名字>/`），浏览器自动携带
会话 cookie —— 恶意界面的 JS 与面板自己没有任何边界：`fetch('/api/state')`、
`fetch('/plugins/别的插件/api/config')` 全部以受害者身份成功。

缓解按成本递增：

1. **文档口径**：商店 / 插件页明示「插件界面能读你的全部面板数据——只装可信来源」
   （一行字，今天就能加）；
2. **隔离子源**：插件界面挂到 `127.0.0.1:<随机端口>` 或沙箱 iframe
   （docs 里「iframe 隔离源」被列为不做——这次演练说明该决定值得复核）；
3. **API 面收敛**：`/plugins/<名>/api/*` 的会话票改为**按插件签发**（一个插件的
   界面拿不到别的插件的 API 权限）。

### P2 SSRF 门不做 DNS 解析（V4）

`ssrf.rs` 的判定是主机名**字符串匹配**（回环名 / .internal / 数字变体 / 单标签），
注释明说「不做 DNS 解析，只能按域名后缀挡」——于是任何解析到回环/内网的公网域名
（localtest.me 这类公共服务，或攻击者自己的 DNS）都能过门。缓解：connect 前
`resolve` 一次并对解析结果 IP 重判（成本：每次出站多一次 DNS；收益：封死这一族绕过）。
短期先在文档标注「SSRF 门按主机名匹配，DNS 层绕过是已知盲区」。

### P2 脚本 = 完全主机访问（V2 / V3）—— **设计边界，接受（2026-11-18 用户拍板）**

脚本任务是普通进程：node:fs / node:sqlite / 全局 fetch 全开——读面板数据库、
auth.json、任意主机文件都是**定义本身**：脚本 = 第三方程序 = 以你的用户权限运行。
应用层围栏（伪装的沙箱、能力白名单）挡不住一个拥有完整进程权限的程序，
**不造假的沙箱**。

缓解只有一层是真的：**容器**。面板整体跑进容器（Docker / podman 镜像）后，
脚本作为面板的子进程被一并关进容器——它能读到的「主机数据」只有容器内的。
产品侧做两件事：

1. 口径进文档与安装提示：安装第三方脚本 = 授予它你的用户权限（本节 + scripts.md）；
2. 给需要隔离的用户提供**官方容器镜像**作为部署选项（远期，进发布工作流的候选）。

不对脚本做应用层沙箱——那会造出一个「看起来有围栏」的假安全感，比没有更糟。

## 攻击链示意（实测复现的最短路径）

```text
用户装了一个带界面的恶意插件
  └─ 打开插件界面（同源页面，浏览器自动带 30 天会话 cookie）
       ├─ fetch /api/state                    → 面板全状态        ✅
       ├─ fetch /plugins/victim/api/config    → 其他插件的账号配置 ✅
       └─ POST /plugins/evil/api/upload       → 数据交给恶意后端   ✅
            └─ 恶意后端 host.fetch 到攻击者服务器（局域网/公网，SSRF 只拦回环/内网段）
                 └─ 外传完成 —— 远程攻击者从此可反复拉取
脚本形态（无界面）更直接：
  └─ node:sqlite 读 panel.db 全库 + node:fs 读 auth.json → POST 给攻击者   ✅
  └─ process.exit(1) 一行杀死面板进程                                     ✅
```

## 结论与处置（2026-11-18 拍板：不修，写清楚）

口径（用户原话）：**插件代码是可信的，第三方脚本由使用者负责，面板只做该做的。**

按这条，上面矩阵里 8 个「成功」的向量**没有一个是面板的漏洞** —— 它们是**插件的权限**：
插件与面板同进程、同一个 `panel.db`、同一份 `process.env`，能跑任意 SQL、能调
`process.exit`、它的界面与面板同源。这些都是产品能力（[plugins.md](plugins.md)「信任模型」），
不是缺陷。要隔离就别在面板里做围栏 —— 把整个面板跑进容器。

第一轮曾按本报告的「缓解」建议收紧了四处，**随后全部回退**（提交 `2448bce` 之后又撤回）：

| 曾收紧的 | 为什么回退 |
|---|---|
| `ATTACH DATABASE` 上限设 0 | 可信插件连自己的库是正常用法；挡住它只是让多库插件报错 |
| `process.env` 白名单 | 实证挡掉了 mgmusic 的 `MGMUSIC_MCLOUD_STORE` 覆盖开关 —— 挡的是正常用法 |
| `process.exit` 改抛错 | 把 Node 的语义改掉；可信插件要退出就是退出，面板靠 launchd 拉起 |
| 出站判定加 DNS 解析 | 每次出站多一次解析；且它只对「恶意插件」有意义 —— 插件是可信的 |

面板**该守**的边界（这部分与本次演练无关，0.6.3 已经收过，见 CHANGELOG 0.6.3 的安全段）：

- `/api/*` 一条不漏地过鉴权（`/api/test/js` 曾经漏了，就是靠守卫 `every_api_route_requires_a_token` 钉住的）；
- `/api/setup` 自己判 Host（挡 DNS rebinding 抢注令牌）；
- 转发给插件 `__route` 的请求头里**不带面板自己的**会话票与令牌（面板不把自己的凭据递出去）；
- 备份恢复校验插件名（`safe_name` 不放行 `.`）；上传/保存的临时文件 `create_new` + 0600；`http://` 装插件必须带 sha256。
