# 调度与性能：任务状态、熔断、时钟、延迟读数

## 任务状态：谁说了算

一条任务有九个字段，来源只有两个：**插件注册**（每次加载时给的）和**人的改动**
（界面上暂停、插件调 `set_job_*`、或 `set_job_schedule`）。热重载和重启之后，
每个字段到底听谁的，这张表是唯一口径 —— 之前只有零散注释，错了两次（第 36、37 轮）。

| 字段 | 来源 | 热重载后 | 重启后 | 备注 |
|---|---|---|---|---|
| `cron`（表达式） | 插件注册 | 插件 | 插件 | 没有覆盖时用注册那条 |
| `override_expr`（调度覆盖） | 人 | **人** | **人** | 落库；插件升级冲不掉 |
| `budget_ms` | 插件注册 | 插件 | 插件 | 面板没有改它的入口 |
| `params` | 插件注册 | 插件 | 插件 | 不落库 |
| `lead_ms` | 插件注册 **或** 人 | 见下 | 见下 | 只有人改过的才落库 |
| `enabled`（暂停/启用） | 人 | **人** | **人** | 落库 |
| `summary` | 人 | **人** | **人** | 落库 |
| `blockers` | 人 | **人** | **人** | 落库；只挡定时触发 |
| `next_fire` | 计算出来的 | 重算 | 重算 | 重启按新起点算下一拍 |

`lead_ms` 的两个来源（第 36 轮）：`register_cron` 的 opts 是**插件默认值**，每次注册都以
插件当时给的为准；`set_job_schedule` 是**人的改动**，落库、热重载和重启都留住。
判断依据是 `lead_override`（`saved_lead()`）。

### 熔断（`tripped` / `trips`）与恢复

语义：**连续失败达阈值就进入冷却**（默认 5 次），冷却结束后半开重试 —— 成功就完全恢复，
失败就把冷却翻倍：30s → 60s → 120s → …（封顶 10 分钟）。所以它不是「永久停用」，
而是「别再把一个必然失败的任务每 30 秒打一次」。

| 事件 | `tripped` | `trips` | 下一拍 |
|---|---|---|---|
| 连续失败 < 阈值 | false | 0 | 按计划 |
| 连续失败 = 阈值 | **true** | 1 | 冷却终点 |
| 冷却后的半开重试也失败 | true | +1 | 冷却翻倍 |
| 半开重试成功 | false | 0 | 重新对齐 |
| `POST /api/tasks/{p}/{n}/reset` | false | 0 | 立刻重算（现在 + 一个周期） |

#### 熔断状态**不落库**：热重载和重启都会清零

`tripped` / `trips` / `consecutive_failures` 只活在内存里。热重载会先 unload（任务列表清空），
再注册 —— 新的任务对象从 0 开始；重启同理。

这是有意的：重启/重载往往是「我刚改完东西」，让熔断从头开始试是合理的。代价是
一个必然失败的任务每次重启都会先失败 5 次才重新熔断。要改的话得给 `tasks` 表加列，
目前不做。

#### 为什么必须有「重置熔断」

通知里写着「已熔断 … 检查完可以手动恢复」，但以前**没有这个出口**：`resume` 只动
`enabled`，`trips` 一直累着，越等越久。人把原因修好（重新登录之类）之后只能干等下一次
冷却。第 38 轮补上 `POST /api/tasks/{p}/{n}/reset`（界面任务行上有「重置熔断」按钮），
清了三个计数并把下一拍对齐到现在。

实测（临时面板 8797，`@every 2s` + 每拍必失败）：

```text
t2s..t10s    runs 1→4，tripped=false trips=0
t12s         runs=5，tripped=true trips=1   ← 到阈值
热重载后      tripped=false trips=0 runs=0  ← 状态不落库，重载即清零
POST reset   200，tripped=false trips=0，next_at 距现在 2.0s
重启后        tripped=false trips=0
日志         「任务 t 的熔断已重置（原来 tripped=false trips=0），下一拍按现在重算」
```

### 三个必须记住的坑

1. **落库必须串行**（`Inner::persist` 通道）。两次注册挨着发生（`register_handler` 先、
   `register_cron` 后，最常见的写法）时，如果每次都 `tokio::spawn` 一个写，谁先落库不确定，
   库里可能留下**旧版本**那一行（cron 空、budget 默认值）。
2. **`register_handler` 那条路径不能落库**：它会 `remember`，把内存里 saved 的用户状态换成
   刚建出来的默认值，随后 `register_cron` 的 `apply_saved` 就读不回来了。
3. **卸下插件（`Cmd::Unload`）不能删 `tasks` 里的行**：那是人的改动，重载/再启用还要靠它恢复。
   代价是插件被删掉后留下几行孤儿（只在注册时被读，没有副作用）。

### 实测（2026-11-12，临时面板 8797）

```text
阶段 0  插件注册（5000 / @every 1h / params a）
  cron=@every 1h  budget=5000 enabled=true  lead=0    params={mode:a}   summary=-
阶段 1  人改（暂停 + 摘要 + blockers + @every 2h + lead 2000）
  cron=@every 2h  budget=5000 enabled=false lead=2000 params={mode:a}   summary=人的摘要
阶段 2  插件升级（9000 / @every 3h / params b）→ 热重载
  cron=@every 2h  budget=9000 enabled=false lead=2000 params={mode:b}   summary=人的摘要
          ↑ 面板赢      ↑ 注册赢                          ↑ 注册赢         ↑ 人赢
阶段 3  重启（budget→7000）
  cron=@every 2h  budget=7000 enabled=false lead=2000 params={mode:b}   summary=人的摘要
```

修之前，阶段 2 会把整行打回默认：`@every 3h / enabled=true / lead=0 / 摘要空`——
也就是**点一次「重载」等于清空这个插件的所有设置**，而且一个错都不报。

### 运行中途被停掉（重载 / 卸载）≠ 任务失败

插件重载或卸载时，在途的那次调用会被 `invocation().stop()` 打断，rquickjs 抛 `AbortError`。
这条路径以前当成普通失败处理，有两个副作用：

1. 发一条 `任务 X 失败 — Error: AbortError: invocation 已停止` 的通知（重载一次响一次）
2. **记进熔断的连续失败** —— 重载 5 次就可能把一个毫无问题的任务熔断

现在分开了：

| | 以前 | 现在 |
|---|---|---|
| 运行记录 | `status=error`，错误是 `Error: AbortError: invocation 已停止` | `status=cancelled`（第 64 轮改的），错误是 `已停止（插件被重载或卸载）` |
| 日志 | `任务 X 失败: …`（error） | `任务 X 被中止（插件被重载或卸载），这次不算失败`（warn） |
| 通知 | 发「任务失败」 | 不发 |
| 熔断 | 计入连续失败 | 不计入（按成功对齐节奏） |
| 之后还能跑吗 | 能 | 能（`in_flight` 会被清掉） |

实测（临时面板 8797，handler `sleep(20000)`，跑到 2 秒时热重载）：

```text
run1 status=error dur=2079 err=已停止（插件被重载或卸载）
日志：任务 t 被中止（插件被重载或卸载），这次不算失败
没有再点一次 → run2 200，能跑

连做 6 次「跑到一半重载」：slow tripped=False trips=0 enabled=True，熔断通知 0 条
真失败（throw new Error('真的失败了')）：仍然发「任务 bad 失败 — Error: 真的失败了」
```

判定只看错误文本里有没有 `invocation 已停止`（`cancelled()`），所以**真的**失败、
预算耗尽、加载期被中断都不会被误判（各有各的文案）。


#### 中断是**协作式**的：只有 host op 才是中断点（第 64 轮实测）

`invocation().stop()` 只是置一个标志；真正会抛 `AbortError` 的是**等在这个标志上的 host op**
（`host.sleep`、带超时的出站请求等）。纯 JS 的 `setTimeout` / 死循环不认这个标志。

矩阵（临时面板 8797，两种 handler × 三种动作，都是跑到 0.7 秒时动手，再等 5 秒）：

| handler | 动作（重载 / 卸载 / 删除） | 结果 |
|---|---|---|
| `await host.sleep(4000)` | 任一 | **0.72 秒就断**：`status=cancelled`，错误 `已停止（插件被重载或卸载）`，「跑完了」没打印 |
| `new Promise(r => setTimeout(r, 4000))` | 任一 | **跑满 4.0 秒**：`status=ok`，「跑完了」照常打印 |

所以「重载会让在途调用停下」这句话的准确版本是：**停在下一个 host op**。
插件里如果有长跑的原生 JS 循环，它会把这一轮跑完（面板不会崩：旧 runtime 由那次调用自己持有，
跑完后一起释放）。

`status=cancelled` 是给界面看的：列表里是灰色的「已停止」而不是红色的「失败」，
「只看失败」筛选也会把它排除 —— 它是人点重载的结果，不是插件的毛病。

### 「下次运行」什么时候算、什么时候不显示（第 65 轮实测）

| 动作 | `cron` | `next_at` | 界面 |
|---|---|---|---|
| 初始 `@every 30s` | @every 30s | 现在 +28.4s，随后只随时间缩短 | 显示时间 |
| 热重载插件 | 不变 | **从重载那一刻重算**（+28.7s） | 显示时间 |
| 改计划 → `@every 10m` | @every 10m | 现在 +599s | 显示时间（计划列标「已改」） |
| 暂停 | 不变 | **0** | 「已暂停」+「下次运行 —」 |
| 恢复 | 不变 | 从恢复那一刻重算（+599s），不是回到暂停前那个时刻 | 显示时间 |
| 暂停状态下重启面板 | 不变（落库） | **0** | 「已暂停」+「—」 |

两条都是这一轮改的：

1. **暂停的任务不报 `next_at`**（给 0，界面显示「—」）。以前照旧返回一个未来时刻，
   「已暂停」旁边挂个未来时间，看着像它还要跑。
2. **改计划只认 `expr` 这个键**。以前传 `{"cron": "@every 10m"}` 会被当成「没有 expr = 撤销覆盖」：
   接口 200、`cron` 没变、下一次也没变 —— 又是一次「静默忽略参数」。现在认不出的键直接 400，
   并告诉人该传 `{"expr": "..."}`。

守卫：`saving_a_schedule_rejects_unknown_keys`、`a_paused_task_reports_no_next_run`；
界面上加了一条「暂停后『下次运行』显示 —」（ui-e2e 第 57 条）。

### 并发：一个插件同时只有一个在途调用（第 69 轮实测）

设计前提是「1 插件 1 runtime + 1 Context」，`Loaded.busy` 守着它。实测三条：

```text
同一插件 + 同一任务，同时发 3 个请求
  请求1 → 200 {"ok":true,"run_id":1}
  请求2 → 409 cc 还有任务在跑，本次跳过
  请求3 → 409 cc 还有任务在跑，本次跳过
  运行记录只有 1 条；日志是「进入 #1 … 退出 #1」，没有并发进入

同一插件的两个**不同**任务（busy 是按插件算的）
  a/sleep2 在跑时点 a/other → 409 a 还有任务在跑，本次跳过

三个**不同**插件同时跑 2 秒（应当并行）
  b 开始 +1306ms | c 开始 +1306ms | a 开始 +1306ms
  a 结束 +3308ms | b 结束 +3308ms | c 结束 +3308ms   ← 真并行，不是排队
```

#### 状态码：忙是 409，不是 400

以前两种情况都回 400：

- `X 还有任务在跑，本次跳过`（插件忙）
- `JS 执行通道已满（同时最多 N 段），等前面的跑完再点`（进程级通道满）

它们都不是「请求写错了」，而是**现在不行、等会儿再来**。现在统一 `409 Conflict`
（`scheduler::is_busy_error()` 判定），客户端/脚本能靠状态码分「重试」和「改参数」两条路。
「没有这个任务」仍然是 400 —— 那个改参数才有用。

界面上两条路都走 `act()` → 红色 toast 原样显示后端那句话，不会「点了没反应」。

守卫：`a_second_run_on_a_busy_plugin_is_a_conflict_not_a_bad_request`（先 200、忙时 409、跑完再 200）。

### 时钟往回跳：任务会静默停摆（第 78 轮，已修）

调度器把「下一次什么时候跑」算成**绝对时刻**存着（`next_fire`）。系统时间往回退一小时，
那个时刻就跟着变成「一小时后」—— 任务停摆一小时，**日志里一个字都没有**。
盒子上电没 RTC、NTP 后校正都会撞上；桌面开发永远遇不到（这也是它一直没被发现的原因）。

#### 修法两件

1. **发现回拨**：调度循环每圈记下「上一圈看到的现在」，若本次比上次早 10 秒以上（`clock_went_back`，
   NTP 微调不会有这么大动作），就当时钟被改了 —— 把每条有计划的活任务按「现在」重新对齐（`realign`），
   落库，并写一条 warn：「检测到系统时间往回跳了 N 秒（HH:MM:SS → HH:MM:SS），已把 M 条任务按现在重新对齐」；
   同一条也进顶部黄条（`scope=clock`），因为警告只留在日志里等于没人知道。
2. **睡眠上限 60 秒**（`MAX_SLEEP`）：`next_fire` 可能在三小时后，循环会一直睡到那时 —— 期间时钟被改也发现不了。
   现在最多睡 60 秒就醒来再看一眼（醒来只是一次 `select`，不做任何 IO）。

#### 读数

```text
单测  clock_went_back：回拨 1 小时 ✓、11 秒 ✓、5 秒不算 ✓、往前走不算 ✓
单测  realign 之后 next_fire = 现在 + 一个周期（且比回拨前那个时刻更早）
实跑  @every 5s 跑 20 秒：4 次成功，间隔 4999 / 4999 / 5001 ms（上限没有拖慢节拍）
实跑  只有一个 @every 1h 的任务时，70 秒内循环多醒了 4 圈（其中含 2 次 /api/state 的指令），说明 60 秒上限生效
```

#### 没做的那一步（如实记）

真把系统时钟往回改需要 `sudo date`，这里**没有**执行。所以「检测 → 对齐」这条链路是靠单测 +
代码路径确认的，「60 秒内一定能醒来」是靠实跑确认的。要在盒子上确认，可以：

```bash
sudo date -u 030100001990        # 往回跳一大截（危险操作，仅测试机）
curl -s localhost:8787/api/state | jq '.alerts'   # 应当看到 scope=clock 的告警
```

### 进程被挂起 / 机器休眠之后（第 79 轮实测）

用 `SIGSTOP` / `SIGCONT` 冻结面板进程，等价于「整机睡了一觉」对调度器的影响（进程不跑、时钟照走）。

#### 行为：**补一次，不重放**

```text
任务 @every 5s，冻结 30 秒（中间该丢 6 拍）
  冻结期间      一拍都没跑（进程停着，本来就不会跑）
  恢复那一刻    立刻补跑 1 次（+33.1s），然后按现在的节拍继续（+38.1 / +43.1 / +48.1s）
  跑完一长串？  没有。不会把丢掉的 6 拍一次性重放出来（否则插件会被打爆）
```

**为什么这样是对的**：「@every 5s」表达的是「每 5 秒看一眼」，不是「欠了 6 次账要还」。
重放对抓取类任务是灾难（醒来连着发 6 个请求），对清理类任务是纯浪费。

#### 新增：少了几拍要说出来

以前醒来只有一行 `tick`，用户看不出「中间少了 6 拍」。现在会多一条 warn：

```text
warn 任务 t 中间少了 5 拍没跑（进程被挂起或机器休眠过？）已跳过，不补跑
```

算法：从 `trigger_at` 开始按计划往后数，数到「现在」为止有几个下次时刻（`skipped_beats`，上限 1000）。
实测冻结 30 秒、`@every 5s` 报的是 5 拍（取决于相位，5 或 6 都正常）。

守卫：`a_suspended_process_reports_how_many_beats_it_missed`（30s→6、4s→0、5s→1、30 天→1000）。

## 性能：现在的时间花在哪（量过的，不猜）

2026-11-12 实测，debug 构建，10 核机器。要复跑用本文末尾的命令。

### 一次运行的开销 ≈ 0–4ms（跟插件源码大小无关）

同一个 handler（空函数），插件源码一个 136 字节、一个 447 KB：

| 插件 | 源码 | 8 次运行耗时 |
|---|---|---|
| `small` | 136 B | 0ms / 0ms / **1ms**（中位 0） |
| `big` | 447 KB | 0ms / 0ms / **1ms**（中位 0） |
| `sleepy` | 136 B，handler 里 `await host.sleep(200)` | 204ms |

结论：**模块只在加载时求值一次，每次运行不重新求值**（否则 447 KB 的解析时间会体现在
运行时长里）。一次派发的固定开销约 0–4ms：403ms 的 sleep 得到 703ms 的？不会 ——
`sleep(700)` 的运行时长是 703ms，也就是固定开销 ~3ms。

手动派发本身的 HTTP 往返：**~2ms**（`{"ok":true,"run_id":N}` 在 0.0020s 返回）。

### 启动：真面板 7 个插件 0.47s

以 `/api/state` 返回 200 为准（含 DB 打开、插件加载、axum 绑定）：

| 素材 | 启动耗时 |
|---|---|
| 1 个 0.1 KB 插件 | **0.10s** |
| 2 个插件，其中一个是 447 KB（20000 条 `const padN = N;`） | **2.09s** |
| 真面板 7 个插件，共 1.6 MB（mcloud 524K / daily 380K / live 220K / exchange 204K + 3 个小插件） | **0.47s** |

注意第二行和第三行：**慢的不是字节数，是顶层语句条数**。20000 条顶层 `const` 的 447 KB
要 2 秒，而 1.6 MB 的真实插件（几万行但结构紧凑）只要 0.47 秒。所以「插件大就慢」是错的，
「顶层塞了几万条独立语句」才是慢的形状。

### 同一插件同时只允许一次在途调用

`slow` 的 handler 里 `await host.sleep(700)`，连点 5 次：

```text
#1  200  {"ok":true,"run_id":1}          0.0020s
#2  400  b 还有任务在跑，本次跳过            0.0008s
#3  400  同上                             0.0008s
#4  400  同上                             0.0008s
#5  400  同上                             0.0008s
运行记录 1 条
```

这是**设计**（一个插件一个 `AsyncContext`，不能重入），不是并发上限不够。跨插件并发由
[engine.md](engine.md) 的共享通道管（`max(1, 核数-2)`）。

### 时长是怎么算出来的

`runs.started_at`（建记录的时刻，**含排队等 JS 名额的时间**）到 `runs.ended_at`（收尾写的），
`dur = ended_at - started_at`。失败运行也会写 `ended_at`：

```text
id=2 status=error dur=0ms err='Error: boom'      ← 失败也有时长
run 1 slow started 1794473090619 ended 1794473091322   ← 703ms
```

所以界面上「耗时」大 = 从按下/到点，到这场运行真正结束。它包含排队等待，那正是用户
感知到的延迟。要看**为什么慢**：

1. 插件忙 → 日志 `xxx 还有任务在跑，本次跳过`（手动）或排队（定时）
2. 全局 JS 名额满 → 日志 `任务 X 排队中（同时最多 N 段 JS…）`
3. 真是 handler 慢 → 看这次运行的日志（`/api/runs/{id}`）
4. 调度器心跳 → `/api/state` 的 `heartbeat_ms`（预期个位数毫秒）

### 复跑

```bash
## 运行开销：空 handler 连跑 8 次，看 dur
curl -s -X POST localhost:8797/api/tasks/small/t/run -H 'x-panel: 1'
sqlite3 data/panel.db "SELECT avg(ended_at-started_at) FROM runs WHERE plugin='small'"

## 启动耗时
time (PANEL_DATA_DIR=/tmp/x PANEL_PLUGINS_DIR=/tmp/x/plugins ./target/debug/panel-llrt & \
      until curl -s -o /dev/null localhost:8797/api/state; do sleep 0.05; done)
```

### 12 个任务同时到点：有的跑 5 次，有的只跑 3 次

最坏压力测试：12 个插件、每个 `@every 5s`、handler 里 `sleep(4000)`，JS 名额 8 个。跑 26 秒
（理论上每个该跑 5 次）：

```text
p1 p10 p11 p12     各 5 次      ← 排在名额空出来的位置上
p2…p9              各 3 次      ← 每两拍被挤掉一拍
合计 44 次（12 × 5 = 60 才是「都不掉」）
heartbeat_ms 0.042            ← 调度循环本身没被拖慢
```

这是**容量**问题，不是 bug：12 × 4s 的工作量塞进 5s 一轮、8 条车道，必然掉拍。
真正的问题是**以前一条日志都不留**：用户只看到「有的整点任务没跑」，无从下手。

现在会报（按任务 60 秒节流）：

```text
任务 t 落后：1 拍该跑没跑（上一拍还没跑完；同时最多 8 段 JS，任务同时到点时就会排队）
```

配合另外两条已有的日志，掉拍就能定位到具体原因：

| 日志 | 含义 |
|---|---|
| `任务 X 排队中（同时最多 N 段 JS…）` | 拿到了派发，但等名额 |
| `任务 X 落后：N 拍该跑没跑（…）` | 到点了但上一拍还没收尾 / 插件还忙，这一拍被跳过 |
| `xxx 还有任务在跑，本次跳过` | 手动点的，插件正忙 |

要真的不掉拍只有两条路：把 handler 做快，或者少让任务挤在同一个时刻（`@every` 错开、
cron 别都写 `0 * * * *`）。面板能做的是**如实报出来**。

### 运行记录查询：20000 行实测（保留策略的上限就是 20 000，所以这是最差情况）

库是手工塞的 20000 行（plugin 交替 a/b，每 5 行共用一个 `started_at`，专门制造并列），
临时面板 8797，每条查询跑 7 次取中位：

| 查询 | 中位耗时 | 条数 / total |
|---|---|---|
| 默认（id 倒序） | 2.2 ms | 50 / 20000 |
| 按开始时间倒序 | 24.8 ms | 50 / 20000 |
| 按耗时倒序 | 25.8 ms | 50 / 20000 |
| plugin=a + 按开始时间 | 15.3 ms | 50 / 9997 |
| 全文搜 boom | 11.4 ms | 50 / 2857 |
| 搜索 + 翻到第 10 页 | 11.4 ms | 50 / 2857 |

翻页：`limit=500&sort=started_at&dir=desc` 一路翻到底 = 40 页、20000 行、**0 重复、0 漏行、顺序反了 0 处**。
边翻边插新行（每页插 1 条）翻 6 页 600 行，也是 0 重复。

limit 夹取：`0`→1 条、`-5`→1 条、`9999`→500 条（cap），`total` 不随游标和 limit 变。

查询计划（`EXPLAIN QUERY PLAN`）

```text
默认 id 倒序                     SCAN runs                ← 逆着 rowid 走，够快
按 started_at 排序（无筛选）      SCAN runs USING COVERING INDEX runs_plugin_started
                                 + USE TEMP B-TREE FOR ORDER BY
带 plugin 筛选 + 按开始时间       SEARCH runs USING COVERING INDEX runs_plugin_started (plugin=?)
                                 + TEMP B-TREE FOR LAST TERM OF ORDER BY
```

结论：**不加索引**。按开始时间排序要多一次临时排序（20000 行的排序 ~25 ms），
但保留策略把表钉在 20 000 行，这个值不会随使用时间变差；为一个点列的排序多养一个索引
（每次插入都要维护）不划算。真要再快，加 `runs(plugin, started_at DESC, id DESC)` 才能同时消掉
两边，那是另一个权衡。

这条下限靠一个守卫钉着（并列值靠 `id` 兜底，见 pitfalls 第 42 条）。

### `/api/state` 与界面刷新：30 个插件实测（第 76 轮）

担心的是「插件多了以后，界面每 5 秒刷一次会变慢」。量完结论是**不必优化**：

```text
插件数   /api/state 中位   /api/plugins/files   state 体积   启动     RSS    浏览器 refresh()
  7          2 ms              2 ms             2.8 KB      0.1 s    31 MB        —
 30          4 ms              3 ms             11.1 KB     0.23 s   40 MB     9–12 ms（1572 个 DOM 节点）
```

配套读数：

- `/api/runs?limit=50` 1 ms、`/api/logs?limit=200` 2 ms —— 和插件数量无关（属于不同的连接）。
- 线程数 **13 个，7 个插件与 30 个插件一样**（tokio 多线程，不是「一插件一线程」）。
- 每多 23 个 runtime 只多 9 MB RSS（LLRT 每插件一个 runtime，这是它的代价，可以接受）。
- 浏览器里 `refresh()` 9–12 ms、切页 1 ms；按 `POLL_MS = 5000` 算，占用约 **0.2%** 的时间。

复跑方法：生成 N 个插件（每个 5 个界面文件）+ 一个 `t` 任务，起面板后对 `/api/state` 连打 12 次取中位；
浏览器侧用 CDP 在页面里 `await refresh()` 计时。

**还没量过的**（记在这里免得以后重复）：30 个插件**同时全忙**时的 `/api/state`
（`sched.memory()` 每个插件最多等 2 ms，最坏 60 ms），以及 release 构建下的同一组数字（上面都是 debug）。

### release vs debug（第 77 轮实测，同一台机器）

| | release | debug |
|---|---|---|
| 二进制 | 31 MB | 92.6 MB |
| 启动到 `/readyz`（7 插件，缓存热） | **0.09 s** | 0.27 s |
| 启动（30 插件） | 0.13 s | 0.17 s |
| RSS（7 / 30 插件） | **19 / 29 MB** | 31 / 40 MB |
| `/api/state` 中位（7 / 30 插件） | **1.1 / 2.1 ms** | 2.1 / 4.7 ms |
| `/api/plugins/files` 中位（7 / 30） | 0.9 / 1.5 ms | 1.6 / 2.9 ms |

**冷启动单算**：release 二进制第一次 exec 是 1.65 s（32 MB 要从磁盘读进来），第二次起 0.09 s。
盒子上电后第一次启动会看到前者，之后重启看到后者。

### 全忙时的 `/api/state`（第 77 轮，30 个插件各跑 4 秒）

```text
空闲            7–10 ms（debug，30 插件）
全忙（改之前）  41–50 ms      ← sched.memory() *串着*一个个等，最坏 N × 2ms
全忙（改之后）  首个请求 45 ms（那一刻正在派发 30 个任务，是别的活），之后 9–12 ms
量到的插件数    22 / 30（其余正忙，记忆量不到，报 null 而不是 0）
```

改法：`Cmd::Memory` 里用 `join_all` 并发量，而不是 `for p in plugins { p.memory_usage(wait).await }`。
语义没变（量不到的还是 `None`，汇总时跳过），只是最坏耗时从 N × wait 变成 wait 量级。
