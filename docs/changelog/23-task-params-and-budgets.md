## 16.26 两个「测出来才知道」的数字（第二十三轮）

写 `worker_hint` 的验收脚本时顺带量出来的，都不影响功能，但**不写下来下一个人会重新踩**。

### ① cron 表达式的任务比 `@every` 晚 3-9ms

同一台机器、同一个进程、同样 1 秒一次：

| 写法 | lateMs（p50 / max） |
|---|---|
| `every('t', '1s')` | **0-1ms** / 2ms |
| `register_cron('t', '*/1 * * * * *')` | **8ms** / 9ms |
| `register_cron('t', '*/2 * * * * *')` | 8ms / 9ms |

**不要**据此认为 `@every` 更准 —— 它的 0ms 有一半是**参考系造成的假象**：
`@every` 的网格是「上一次实际触发 + 周期」（`scheduler.rs` 的 `next_after(base)`），
所以网格自己跟着延迟漂，`lateMs` 自然接近 0。用绝对时刻量才看得清：
`@every` 报 `scheduled=.784 → fired=.785`（真准，1ms），
cron 报 `scheduled=.000 → fired=.009`（真晚 9ms）。

根因没定位。已知的相关事实：面板有一个 **1Hz 的 tokio ticker**
（`main.rs`，广播 `EngineCmd::Tick` 给每条 worker），而 cron 的网格正好落在整秒上；
`recv_timeout` 在「先被 tick 提前唤醒、再睡一次」之后实测会过冲 8-10ms。
`@every` 的网格一般不在整秒上，撞不上 tick。

**为什么先不修**：cron 本来就是秒级表达式，秒级任务晚 9ms 没人能察觉；
真要毫秒级精确的场合（抢兑），做法是**提前几十秒启动任务、由插件自己在任务内部计时**
（mcloud 就是这么做的：`hh:59:40` 进窗口，然后自己等到整点），
面板这一枪晚几毫秒不影响结果。真要修的话方向是「到期任务先触发、再处理收到的命令」。

### ② 夹具的网格相位能让测试「看起来通过」

第一版验收脚本的阻塞夹具用的是 `@every 2s`，抢兑夹具用的是 cron（整秒）。
两次运行给出 **139ms** 和 **9ms** —— 因为 `@every` 的网格是「加载时刻 + 周期」，
相位随启动时刻变，**大部分时候和整秒网格根本不相撞**，夹具压根没挡住人。

改用 `*/1 * * * * *` 让两者落在同一条网格上之后，结果稳定在 310ms（挡住）/ 9ms（隔离）。

**教训**：做 A/B 对照时，两个任务的**时间网格必须对齐**，否则测的是运气。
（这和 [§16.19](14-15-throughput-and-editing.md#1619-卡片头部布局改两次才对用户两次实测指出) 那条「空样本也算过」是同一类：断言绿了但什么都没测到。）

## 16.27 任务参数：同一个处理函数挂多条任务（第二十三轮）

**问题**：抢兑要求所有账号**并行**发单 —— 串行会错过那几百毫秒的窗口。而面板只能把
「一条任务」派给引擎。之前只能靠插件自己在 handler 里循环账号，那就必然串行。

**做法**：任务带上参数。插件注册 N 条任务（名字不同、处理函数相同、`params` 里各带
一个账号），面板照常调度，每条任务自己带上自己的参数。

```js
for (const account of ['alice', 'bob', 'carol']) {
    register_cron('exchange-' + account, '*/1 * * * * *', doExchange, { params: { account } });
}
function doExchange(p) { log(p.params.account); }   // 不用自己 JSON.parse
```

**几处刻意的设计**：

| 决定 | 为什么 |
|---|---|
| 参数存**文本**（`jobs.params`），面板不解析 | 面板**不理解**它的内容，只负责原样存、原样透传。否则「面板要认识插件的数据结构」这层耦合就来了 |
| payload 里是**解析好的 JSON 值**，不是字符串 | 插件那边 `p.params.account` 直接取；塞字符串的话每个 handler 都得自己 `JSON.parse`，很容易忘 |
| 没给参数 → `null` | 不是 `{}`、不是 `undefined`。三者语义不同，含糊会让人写出 `p.params?.x ?? y` 这种防御代码 |
| `sync_jobs` **收敛** `params` | 「有哪些账号」只有插件知道；账号变了重新声明一次就该同步过去。（不像 `paused` / `deleted` 那样要保住用户意图） |
| 加载期校验可序列化 | 循环引用之类的值在**注册时**就报错，不会等触发时才在 payload 里变成 `null` —— 静默是这里最坏的失败模式 |
| 面板建的参数上限 64 KiB | 参数是**任务定义**的一部分，不该拿来当数据仓库用（要存数据用插件自己的 SQLite） |
| `JobSpec` 从 4 元组改成结构体 | 加第 5 个字段时全靠数位置太容易错，字段名自解释、编译器也帮着查 |

**实测验收**（`scripts/params_check.py`，夹具 `examples/params/params.js`）：

```
第一次启动  三条同处理函数的任务各拿到 {"account": "alice"|"bob"|"carol", "slot": 3}
           无参数的那条拿到 null · 数组参数那条拿到 ["x", 1, true]
           三条没串味（账号互不相同）
重启之后    五条任务的参数全部原样还在（走 jobs.params 那一列）
面板路径    能建带参数的任务（http 200）· 参数落进 jobs 表 ·
           与插件任务重名会被拒（400）· 超大参数被挡（400）
```

## 16.28 随机表达式：让触发时刻不再整齐划一（第二十三轮）

**问题**：多个用户/实例用同一个表达式（`0 8 * * *`）时会在同一毫秒一起打服务器。
请求尖峰既压垮对端，也让自己的失败率上升。

**做法**：表达式末尾加一个抖动后缀。

```text
@every 1s -200ms          # 实际落在 [t-200ms, t] —— 「提前一点点」
*/5 * * * * * ~500ms      # cron：实际落在 [t-500ms, t+500ms]
0 8 * * * +30s            # 只往后
```

| 记号 | 含义 | `@every` | cron |
|---|---|---|---|
| `-X` | 只提前 | ✅ | ✅ |
| `~X` | 双边 | ❌ 报错 | ✅ |
| `+X` | 只推后 | ❌ 报错 | ✅ |

**几处刻意的设计**：

| 决定 | 为什么 |
|---|---|
| `@every` 只允许**负**偏移，且上限周期的 20% | 提前是安全的：`实际 ≤ 理论 < 下一拍理论` 恒成立，单调性天然保证、**不需要任何钳制**。推后就会跟下一拍打架 |
| cron 宽松（三个方向都行，越界**钳制**） | cron 的理论时刻是绝对日历时刻，钳到相邻槽位内就能保证频率不降。代价是偏移过大时退化成「贴着下一拍」 |
| 记号**不可省** | `@every 5s 1s` 报「记号不能省，写成 `-1s`」。少一个字符是这里的头号错误 |
| 理论线 / 实际线**分开存**（`base_fire` / `next_fire`） | 抖动**不能累积**。拿「上次实际 + 周期」当基准，`@every 1d -30m` 会变成随机游走 —— 跑一个月「8 点」就漂走了 |
| 暂停恢复 / 换表达式 / 熔断重试 / 重新对齐**都不抖** | 抖动只属于「按节奏到点了」。用户刚点完按钮却等一个随机量，很莫名其妙 |
| `scheduledAt` 给**理论**时刻，`lateMs` 扣掉抖动 | 否则 `diag` 那类任务拿 `lateMs` 的 p99 判断「同轮有没有慢任务把我推开」时，p99 会被自己抖出来的数字顶爆。恒等式：`firedAt - scheduledAt == lateMs + jitterMs` |
| 随机源默认系统熵，`PANEL_JITTER_SEED` 可复现 | 排障要能重放。用「种子 + **理论时刻**」而不是自增序号 —— 理论时刻由表达式确定算出、跨重启稳定，复现不需要额外存状态 |

**实测验收**（`scripts/jitter_check.py`，夹具 `examples/jitter/jitter.js`）：

```
带抖动（@every 1s -200ms，12 拍）
  抖动方向恒为负 · 幅度 ≤200ms · 取值真的在变 · 11/12 拍提前
  lateMs 均值 6ms ← 关键：混进抖动的话均值会是 -100ms 上下
  firedAt - scheduledAt == lateMs + jitterMs 全部成立
  实际触发严格递增 · 相邻间隔 824~1182ms（没挤在一起也没漏拍）
对照组（无抖动）
  jitterMs 恒为 0 · lateMs 均值 0.8ms ← 没有回归
cron（*/1 * * * * * ~200ms）
  lateMs 均值 6ms · 抖动在 ±200ms 内 · 相邻间隔仍为正（钳制生效）
可复现（三个实例同时跑）
  同一种子在 12 个共同理论时刻上给出同一偏移
  换个种子 11/12 个时刻不同
```

> 判据为什么看**均值**而不是单拍最大值：泄漏的表现是「每一拍都被挪了 `jitterMs`
> 那么多」，均值会整块偏掉（约 -100ms）；而机器忙的时候偶尔有一拍迟到 60ms 是
> 正常的调度噪声。第一版写的是 `max(|lateMs|) < 50`，在全套验收连跑时误红过一次。

> 可复现性判据有**两个前提**，缺一个就测不出东西：① 必须用 cron —— `@every`
> 的理论时刻从**进程启动那一刻**起算，两次运行基准不同；② 三个实例必须**同时**
> 跑 —— 分别跑覆盖的是不同的秒，根本没有共同时刻。（这两个坑都是写脚本时真踩到的。）

## 16.29 插件声明的侧边栏入口（第二十三轮）

**问题**：插件有自己的页面，但面板只能把它藏在「插件管理」页里一个按钮后面。
用户要「打开日常任务」，得先找到插件管理、再从一堆插件名里认出 `mcloud-daily` ——
**这正是「界面完全搞不懂」的一半**。

**做法**：插件自己声明一个侧边栏入口。

```js
register_nav({ label: '日常任务', icon: '🗓' });   // path 不给就用 {name}/index.html
```

**几处刻意的设计**：

| 决定 | 为什么 |
|---|---|
| 名字由**插件**给，面板不推导 | 面板已经能推导出「有没有配置页」（`{name}/index.html` 存在），但**推导不出该叫什么**。面板替它起名 `mcloud-daily` 的话，用户看到的是一串插件文件名 |
| 用 **iframe** 而不是注入插件的 JS | 插件是操作者自己装的代码。注入主页面等于让它能改面板本身（读令牌、改别人的任务）。iframe 是同源但**独立文档**，影响范围就那一块 |
| 页面位置复用**已有**的约定 | `{name}/index.html` 这条规则只写在一处 —— 面板判断「有没有配置页」和「实际能不能打开」必须用同一个判据，否则就是「按钮点了 404」那种最难查的错 |
| 一个插件**只能声明一个**入口 | 第二个报错而不是静默覆盖。侧边栏是给用户认路用的，悄悄多一项或少一项都让人困惑 |
| **停用的插件不摆入口** | 引擎没加载它、页面也打不开。给一个点了 404 的入口是最差的可达性（判据与插件列表里那处一致） |
| 入口按**内容变化**才重建 DOM | 这段跟着 5 秒轮询跑，每次重建会把用户正按着的 `<a>` 换掉（移动端滑出侧边栏时那一下点击就丢了），还白费一次重排 |
| `label` 按**字符**数限长（12） | 按字节数的话中文 label 会被误杀（一个 CJK 字 3 字节） |

**实测验收**（`node scripts/nav_check.mjs`，夹具 `examples/nav/`）：

```
接口层   navdemo 已加载 · nav 声明带回来了 {"label":"日常任务","icon":"🗓"} ·
        没写 path 落到 /plugins/navdemo/index.html · 对照插件没有 nav 字段 ·
        页面可访问（200）· 插件自己的接口可用
浏览器里 已登录（先确认这条，否则后面全是假红）· 侧边栏有入口区块 ·
        入口用插件给的名字（不是插件名）· 对照插件没多出入口 ·
        点击 → #/plugin/navdemo · iframe 指向插件页面 · 标题用插件给的名字 ·
        那一项被高亮 · **iframe 里的页面调通了插件自己的接口**
停用后   入口消失 · 整个区块隐藏
```

> 脚本里踩到的坑：cookie 名字**写死成 `session`** 而服务端叫 `panel_session` ——
> 浏览器其实没登录，SPA 把整页换成登录视图，于是所有 DOM 断言都在对着一个
> 不存在的 DOM 跑。现在 cookie 名从响应里解析，而且**先断言「已登录」**，
> 免得这类失败被误读成「入口没出来」。

## 16.30 `smtp_send`：推送的邮件通道（第二十三轮）

**问题**：推送有 10 个渠道，邮件是其中之一，而面板此前完全没有发信能力。

**做法**：`smtp_send(opts)` —— 裸 SMTP 客户端，支持 `starttls` / `implicit` / `none`。

**为什么自己写而不是找个库**：插件要的只是「把一封邮件交给服务器」。能用得上的库
要么拖进一整棵异步栈（lettre），要么在 Linux 上引入 OpenSSL（`native-tls`），
与「静态 musl 单文件」这条部署性质冲突。而协议面很窄：`EHLO` / `STARTTLS` /
`AUTH` / `MAIL` / `RCPT` / `DATA` / `QUIT` + MIME 的头编码与 base64。

**零新编译单元**：`rustls` / `rustls-pki-types` / `webpki-roots` / `base64`
本来就在依赖树里（`ureq` 拉的），加为直接依赖**不增加任何编译单元** ——
和 `getrandom` / `blake2` 是同一条理由。信任库与 `http_fetch` / `ws_*` 同一份，
「目标机不需要装 CA」对邮件也成立。

**几处刻意的设计**：

| 决定 | 为什么 |
|---|---|
| 用 rustls 的**同步** API（`StreamOwned`） | 插件侧全是阻塞调用，与 `http_fetch` 同构比省一条线程重要 |
| `tls` 拼错**报错**，不默认成 `none` | 默认成 `none` 会明文把密码发出去 —— 最坏的失败模式是静默的 |
| 端口不给就按 `tls` 推（465 / 587） | 少一个要填的格子，而填错的代价是「连不上」这种没头绪的报错 |
| 失败时把服务器**原话**带回来 | `535 bad credentials` / `550 no such user here` 贴进日志就能排查；自己编一句「发送失败」等于把信息丢了 |
| 收件人被拒时**点名**是哪个地址 | 群发时最要紧的信息 |
| `ca_file` 是**追加**信任锚，不是替换 | 「内网用私有 CA」和「外网用公共 CA」经常同时存在，替换会让一半忽然连不上 |
| **不做附件** | 要处理 filename 编码、Content-Disposition、各家客户端对 MIME 的奇葩解读 —— 另一个量级的复杂度，而推送只需要「一段文字」 |

**实测验收**（`python3 scripts/smtp_check.py`，自带假 SMTP 服务器 + 真邮件解析器）：

```
明文 + AUTH PLAIN   MAIL FROM/RCPT TO 正确 · 中文主题 RFC 2047 往返无损 ·
                   显示名可解析 · Message-ID / Date 有 · 正文往返无损
只给 AUTH LOGIN     自动退回 LOGIN 机制 · `to` 收字符串也认
text + html         multipart/alternative · 两段都在且各自无损
点填充              正文里行首的 `.` 原样到达（邮件没被截断）
失败路径            密码错→带回 535 原话 · 收件人被拒→点名地址 ·
                   没声明 STARTTLS→给出可操作的报错 · 连不上→报错而不是挂死
STARTTLS            私有 CA 签的证书 + ca_file 走通 · 不给 ca_file 则被拒
implicit TLS        走通 · 主题正文无损
```

**测试抓到的两个真 bug**（都是「不看真服务器就发现不了」的那类）：

1. **`MAIL FROM:<机器人 <a@b>>`** —— 信封（`MAIL FROM` / `RCPT TO`）只认**裸地址**，
   把头里那个 `显示名 <a@b>` 整个塞进 `<>` 会变成两个 `<` 加一个没闭合的尖括号。
2. **`Conn::writer()` 里写了 `get_mut().get_mut()`** —— 那是拿到**底层 `TcpStream`**，
   等于绕过 TLS 明文发命令。握手本身由第一次读驱动所以能成功，之后每条命令都是明文，
   服务器在记录层直接崩（`record_overflow`），而报错看起来像是服务器的问题。
   **这个 bug 只有对着真的 TLS 服务器跑一遍才会露出来。**

> 脚本侧也踩了两个坑：假服务器用 `makefile().readline()` 会**预读**，
> 把紧跟 `220` 之后到达的 ClientHello 吞进自己的缓冲 —— 改成逐字节读行；
> `openssl req -x509` 生成的证书默认带 `CA:TRUE`，rustls 会当成 CA 而不是服务器证书
> （`CaUsedAsEndEntity`），要生成「私有 CA + 它签的叶子证书」才对。

## 16.31 按任务/路由声明执行预算（第二十三轮）

**问题**：面板只有一个**全局**执行预算（`EXEC_BUDGET_MS`，默认 2000ms），超了直接报
「疑似死循环」掐断。这是当年被迫把插件写成「一次调用只走一步」的状态机的根因 ——
一个「一个函数从头跑到尾」的任务必然超过 2 秒。

**做法**：`register_cron(…, { budget_ms })` 与 `register_route(…, { budget_ms })`。

```js
worker_hint('exclusive');                       // 长预算必须配独占线程
register_cron('日常', '*/30 7-22 * * *', runDaily, { budget_ms: 120_000 });
```

**几处刻意的设计**：

| 决定 | 为什么 |
|---|---|
| 上限 10 分钟，越界**报错** | 预算不是「取消超时保护」的口子，它解决的是长任务被误杀 |
| 没声明预算的任务**依然**被全局值拦下 | 保护还在 —— 验收脚本里有一个对照组专门验这件事 |
| 预算**跟着代码走**（`sync_jobs` 收敛它） | 它是任务定义的一部分，不是用户意图；保留一个旧预算 = 插件改了但没生效 |
| 长预算 + 没 `exclusive` ⇒ **加载期警告并点名** | 那个症状出现在**别的插件**身上（它们的任务忽然变慢），没人会想到是刚装的那个 |
| HTTP 层也读声明的预算 | 否则「声明了 8 秒、HTTP 3 秒就 504」，声明等于没声明 |

**实测验收**（`python3 scripts/budget_check.py`，14 项断言）：

```
路由    声明预算的 4 秒处理返回 200（确实跑满 4 秒）· 短路由照常
任务    声明预算的 4 秒任务跑完 · 没声明预算的依然被全局 2 秒掐断
落库    budget_ms 进 jobs 表 · 没声明的为空
警告    长预算 + 没 exclusive ⇒ 点名 overbudget · 长预算 + exclusive ⇒ 不警告 ·
       没声明预算 ⇒ 不警告
```

**验收脚本抓到的两个 bug**：

1. **HTTP 那一层用的是全局预算** —— 路由声明了 8 秒，Axum 侧仍在 3 秒就 504
   （`插件路由 … 超过 3s 没返回`）。两处都要读声明的预算。
2. **`db::insert_panel_job` / `sched.add` 的调用点全靠数位置** —— 加参数时
   `params![]` 的占位符数量对不上。这是第二十三轮第二次在同一个地方踩坑
   （`JobSpec` 改成结构体就是为了这个），说明**结构体化的方向是对的，
   只是测试里的调用点还在用位置参数**。
