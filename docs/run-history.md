## 24. 运行记录：从"那次执行"点进日志（第二十六轮）

日志是**插件层次**的：插件想打什么打什么，一天一个文件、保留一周。
运行记录是**面板层次**的：谁在什么时候跑了哪条任务、成没成、花了多久 ——
面板自己写，插件改不了、也删不掉。

这一轮把两者接上，但**不合并**：它们各有各的保留期、各有各的用途。

> 第六十轮补充：**脚本任务**的一次执行也写同一张 `runs` 表，但它的输出**不进日志库** ——
> 合并的 stdout/stderr 存在 `runs.output` 里（形状与测试运行一致）。所以脚本的运行记录
> 不能「点进日志」，直接看记录自带的输出。见 [script-jobs.md §6](script-jobs.md#62-一次执行的生命周期)。

### 24.1 那根线只有一个：`runs.id` == 日志的 `run_id`

```
runs 表（面板）                      日志（插件）
┌────────────────────────────┐       ┌──────────────────────────────────┐
│ id   20261015-214409-0000  │──┐    │ run=20261015-214409-0000 …       │
│ task fs-demo-tick          │  └───▶│ run=20261015-214409-0000 …       │
│ ok   true · 1 ms           │       │ run=None …（插件加载时的日志）    │
└────────────────────────────┘       └──────────────────────────────────┘
```

引擎执行一条任务时用 `log::with_run_id(&run_id, …)` 圈住**整段执行** ——
那期间插件打的每一行都带上这个 id，**包括面板自己对这次运行的结论**
（"手动触发成功"/"执行失败: …"）。失败那条尤其重要：点进日志的人最先要找它。

于是"从记录点进日志"就是把 id 交给日志页过滤（`#/logs/run/{id}` → 服务端按
`run` 过滤）。**没有第二种关联方式** —— 靠时间戳猜是猜不准的，靠消息文本匹配
更是碰运气。

### 24.2 运行 id 的形状是被需求逼出来的

```
20261015-214409-0000
└─ 时间前缀 ──┘ └序号┘
```

- **URL 安全**：它要进 `#/logs/run/{id}`，所以只用 `[0-9a-f-]`；
- **同进程内绝不重复**：靠自增计数器，不靠随机数（随机数只是"大概率不重复"）；
- **跨进程可排序**：时间前缀，重启后看记录仍按时间顺序。

### 24.3 保留期**故意不一样**：日志 7 天 / 记录 30 天

这不是随手写的两个数字。如果记录和日志一起删掉，那个"日志过期"的状态就永远
观察不到 —— 记录凭空消失，用户只会以为面板漏记了。

所以记录活得比日志久，界面才能说清楚：

| 状态 | 界面说的是 |
| --- | --- |
| 记录在、日志在（内存环或 JSONL） | 正常显示那次运行的所有行 |
| 记录在、日志已清理 | **「这次运行的日志已过期（日志保留 7 天，运行记录保留 30 天）—— 记录还在，日志文件已经清理掉了。」** |
| 记录不在（>30 天或手拼的 id） | 「没有这条运行记录」（**和上一句是两回事**，不能混着说） |
| 记录在、日志为空但没过期 | 「这次运行没有产生日志」 |

#### 两个闸门，取先到者（issue #9）

天数**单独一个维度兜不住高频任务**：`@every 50ms` 一个任务 30 天能写 **15 GB**
（实测约 **271 字节/条**，3 小时合成负载写进 63.4 MB），而低配设备正是这个产品的
目标机型。所以还有第二个闸门 `RUN_KEEP_ROWS`（默认 **20 万条 ≈ 54 MB**）：

| 闸门 | 默认 | 触发时 |
|---|---|---|
| `RUN_KEEP_DAYS` | 30 天 | 删比这更早的记录 |
| `RUN_KEEP_ROWS` | 20 万条 | 行数超了就从**最老的**开始删（按 `started_at`，不是按 `id`） |

正常情况下第二个闸门不会触发 —— 一天几十次任务的话，20 万条够用几年。
它只在「有毫秒级任务」这种场景下起作用。设 `RUN_KEEP_ROWS=0` 可关掉它。

**怎么知道自己有没有长胖**：`/api/state` 里的 `storage` 块，
`runs_rows` 是行数、`db_bytes` 是主库体积。以前只能靠外部脚本 `stat` 文件才发现。

判据是**运行时间 vs 保留期**，不是去问文件在不在：文件可能被手工删掉，
那时候说"过期"同样是对的（对用户来说就是没了）。

运行视图打开时，先按 run id 读 `logs/plugin-YYYY-MM-DD.jsonl`，再接 SSE 看新行。
SSE 只回灌**内存环**；面板一重启，旧运行的日志还在文件里、内存里却没有 ——
不回文件就会把"日志在盘上"误报成"没有产生日志"。历史读取有 5000 行上限，
接口返回的字段与 SSE 的 `log` 事件一致，前端复用同一套渲染。

### 24.4 失败必须有记录

失败的那几次恰恰是最需要点进日志的。所以：

- 失败也写记录（`ok = 0`），并把**错误文本**一起存进 `runs.error` ——
  日志过期之后，那一格是唯一的线索；
- 面板重启时把**上一轮没结束**的记录收尾（`close_dangling_runs`）：
  不收的话它们会永远显示成"跑着呢"，而那次运行早就没了 ——
  界面在撒谎比没有界面更坏。

### 24.5 记录写不进去，不挡执行

`insert_run` / `finish_run` 失败只打一条 warn。任务是正经活，记录只是账本 ——
反过来（因为账本写不进去就不干活）是本末倒置。

### 24.6 界面

- **任务卡片 → 「记录」**：该任务最近 30 次运行（结果 / 开始时间 / 触发方式 /
  耗时 / 运行 id），失败的行下面直接跟一条红色错误文本；
- **每条记录 → 「看日志」**：跳到 `#/logs/run/{id}`；
- **日志页顶部的横幅**：这次运行是**面板的记录**（哪条任务、几点、成没成、
  多久），下面的终端区才是日志。两者视觉上分开，因为它们在数据上就是两回事。

```

             清单里有而模块体没有 → 插件 import 拿到 undefined；
             反过来 → require 能用、import 不能用（更难查）。两种都不会再发生。
             这条测试**验过会红**：塞一个假的 `watchFile` 进去，它当场报
             「导出清单里有 watchFile，但模块体里没定义」）
冒烟       396 项（新增 17）：「运行记录」一组

             运行 id 是 URL 安全的形状（正则钉死）
             **那次运行的日志真的带上了那个 id**（不带的话"反查"是空话）
             插件自己打的行也带（不只是面板的结论行）

## 26. 试跑也进运行记录（第二十六轮续）

上一节把「测试运行没有历史」记成欠账。这一节还账。

### 26.1 试跑和真跑**不是一回事**，记录却是同一张表

| | 真跑（cron / manual） | 试跑（test） |
| --- | --- | --- |
| 谁触发 | 调度器到点 / 面板点「立即执行」 | 任务编辑器里按「运行测试」 |
| 解释器 | 插件**常驻**的那个（带着它的状态） | 一次性临时解释器（不碰任何插件状态） |
| 输出去哪 | **日志库**（终端 + 环形缓冲 + JSONL），带 `run` 标签 | **捕获缓冲**，只回给 HTTP 响应 |
| 记录里存什么 | 结果 + 耗时 + 错误 | 结果 + 耗时 + 错误 + **输出本身** |
| 界面给什么入口 | 「看日志」（跳到 `#/logs/run/{id}`） | 展开看输出（**没有**看日志） |

最后一行是这一轮最容易做错的地方：**给试跑一个「看日志」按钮，点进去是空页面** ——
用户会以为日志丢了。真相是试跑的输出根本不进日志库（`log/capture.rs`：
不打终端、不进环形缓冲、不写文件）。所以试跑的记录**自己存一份输出**
（`runs.output`，8 KB 上限、按字符边界截断），界面给的是展开。

### 26.2 上下文：试跑属于哪条任务

`POST /api/test/{lang}` 的请求体多了两个可选字段 `plugin` / `task`，任务编辑器
会带上（编辑已有任务时两个都有；新建任务时只有 plugin）。

为什么要带：试跑和真跑是**同一条任务的两半** ——「改了代码 → 试跑 → 保存」本来
就是一串。「记录」里能看到：

```
成功  2026-10-15 22:37:17  试跑   3 ms  20261015-223717-0002  试跑（输出见下）
                            └ 展开：试跑输出 2
                                    --- stderr ---
                                    试跑 stderr
失败  2026-10-15 22:37:17  试跑   2 ms  20261015-223717-0001
                            Error: 试跑故意炸
成功  2026-10-15 22:30:00  调度   1 ms  20261015-223000-0000  看日志
```

不带上下文（以后的通用试跑框）就记到 `__test__` 名下：它在全局列表里，但不会
混进任何任务的记录 —— **记录找不到入口就是噪音**，所以归属是明确的。

### 26.3 为什么不复用 `insert_run` + `finish_run`

真跑分两步写（先"开始了"、跑完补结果），是因为中间有"面板被杀"这种窗口，
那条没收尾的记录本身就是要能看见的信息。

试跑**没有那个窗口**：HTTP 请求一直等到跑完才返回。所以一次写全
（`insert_test_run`）更简单，也不会出现"跑完了但收尾失败"的半截记录。

### 26.4 证据

```
冒烟 403 项（新增 7）：
  试跑接口 200 · 试跑留下 kind=test 记录 · 记录里写了成功
  **试跑的输出存在记录里**（日志库里没有它）· stderr 带来源标记
  **试跑的输出没有进日志库**（这条是设计的断言：进了就说明捕获缓冲没生效）
  失败的试跑也记下来并存了错误文本
浏览器 8 条断言：记录里标出「试跑」· 试跑那行是提示不是「看日志」
  点开后能看到输出内容（含 stderr）· 展开处写了输出大小
  **真跑的记录仍然有「看日志」**（别把试跑的规则套到真跑上）
  弹窗说明写清了试跑为什么没有看日志
```

## 27. 「停止」不是失败（运行结果的第三种状态）

### 27.1 症状：用户按了停止，看到的是「面板炸了」

手动停止（或超出执行预算）时，引擎打断 JS，QuickJS 抛的是
`InternalError: interrupted` 加一整段调用栈 —— 和**真正的报错**走的是同一条路。
于是那次运行被当成失败：

- 运行记录里是红色徽章 + 一屏堆栈；
- 连续失败计数 +1，停几次就可能把任务**熔断**；
- 任务状态变「执行出错」（下次到点还会被当成「上次出错」）；
- 推送里发一条**失败告警** —— 用户自己按的停止，等于自己给自己报警。

用户的原话是「停止不能搞的页面报错一样」。对：停止是**用户的操作**，不是任务出了故障。

### 27.2 判定只有一处：`runs.stopped` + `runOutcome()`

```
ok=1                 → 成功
ok=0, stopped=1      → 已停止（中性，不是失败）
ok=0, stopped=0      → 真失败（红色，带原因）
ok=NULL              → 没跑完（面板重启留下的残记录）
```

- 后端：`runs` 加一列 `stopped`（`ensure_column` 补列，老库默认 0 —— 历史记录本来就
  全是真失败）。`finish_run` 多一个参数，停止时不写 `error`（那句 interrupted 不是「原因」）。
- 判定依据是 `Watchdog::task_stop_requested()`：停止和预算到点在引擎里是**同一个中断**，
  所以对外都算「已停止」，界面上那句说明也是这么写的（不谎称一定是手动停止）。
- 前端：`web/js/status.js` 的 `runOutcome(run)` 是唯一判定处，运行记录弹窗（任务页 / 脚本页）
  和日志页横幅共用。它还认老记录 —— 只有 interrupted 文本、没有 stopped 标记的行，
  同样显示「已停止」，升级后不会突然变红。

### 27.3 分流：记录 / 推送 / 调度 / 日志

| 位置 | 停止时 |
| --- | --- |
| `runs` | `ok=0, stopped=1, error=NULL` |
| 连续失败计数 / 熔断 | 不 +1（传 `None` 给调度器），任务状态保持「已启用」 |
| 推送 | **不发**（日志里留一条「已停止，不发推送」） |
| 日志 | 一条 info：「已停止（手动停止或超出执行预算），耗时 Nms」 |

### 27.4 证据

```
前端资源检查 287 项（新增 4）：
  被停下的运行显示「已停止」，不是红色失败，也不把 QuickJS 堆栈摆给用户看
  老记录（只有 interrupted 文本）也按「已停止」显示，升级后不会突然变红
  真正的报错仍然显示「失败」并带原因 · 成功的运行显示「成功」

cargo test 451 项通过

端到端（临时实例 + 一个死循环任务，跑 1.5 秒后 POST /stop）：
