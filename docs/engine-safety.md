## 7. 执行预算与熔断（引擎自我保护）

插件是不可信代码。这一节讲宿主怎么保证「一个坏插件不会把整台设备带走」。

### 7.1 QuickJS：一个死循环插件能拖垮整个引擎（修复前的 P0）

`examples/hostile-plugins/` 专门用来复现这个问题（不在默认 `plugins/` 里，需显式 `PLUGINS_DIR`）。

修复前实测：

| 观测项 | 现象 |
|---|---|
| 任务触发 | 全部停摆（`runaway` 的 runs 永远停在 0） |
| CPU | 烧满一个核（99.3%） |
| HTTP 面板 | **仍然返回 200**，`/api/state` 还报 `"status":"running"` |
| `SIGINT` / `SIGTERM` 优雅退出 | **无效**，`engine.shutdown()` 里的 `join()` 永久阻塞，只能 `kill -9` |

根因：调度器、所有 QuickJS 插件、所有任务跑在**同一个引擎线程**上，而 QuickJS 侧没有设
interrupt handler，`while(true){}` 会永久占住该线程。附带后果比卡死本身更糟 ——
**监控会撒谎**：面板显示「运行中」，实际引擎已经死了。

**修法**：

1. **执行预算**：注册 Runtime 级的 interrupt handler（`rt.set_interrupt_handler`）。
   每次调 JS 前 `arm(budget)`、调用后 `disarm()`，超时由 QuickJS 抛异常打断。
   覆盖三个入口：插件顶层 `eval`、`on_tick`、cron handler。
   默认 2000ms，环境变量 `EXEC_BUDGET_MS` 可覆盖。
2. **关闭优先**：`EngineHealth.request_stop()` 置位后 handler 无条件打断。
3. **健康上报**：`EngineHealth` 同时跟踪「最近心跳」和「预期唤醒时刻」，**两者都过期**
   才判 `degraded`。只看心跳会把「调度器睡 1 小时等下一个任务」误判成卡死；
   只看预期唤醒则判不出「卡在 JS 里」。
4. **SIGTERM 支持**：`systemctl stop` / `docker stop` 发的是 SIGTERM，只监听 SIGINT 不够。

修复后实测：

| 观测项 | 修复前 | 修复后 |
|---|---|---|
| 同目录对照组 `alive` 任务 | 停摆 | **runs 持续增长**（7 → 10） |
| `runaway` 任务 | 永久卡死 | 每轮被中断，`last_error` = `执行超过预算 2s，被强制中断（疑似死循环）` |
| 面板状态 | 撒谎报 `running` | 卡死时诚实报 **`degraded`**（`beat_ago=8027ms`） |
| 优雅退出（SIGTERM） | 卡死，只能 `kill -9` | **1 秒内退出** |

### 7.2 外部 Node / Bun：预算 = 杀进程组

外部解释器没有安全的「暂停一个正在跑的 JS 调用」的手段（V8/JSC 不给你从外部中断循环的钩子，
`SIGSTOP` 只会把整个进程冻住、无法回收）。所以外部插件的执行预算是**硬杀**：

```
dispatch → 写 fd0 invoke → 等 fd1 result
             │
             ├─ 在 budget + 250ms 宽限内返回 → 成功 / 插件报告的失败
             └─ 超时 / 子进程 EOF / 崩溃
                   → SIGKILL 整个进程组（process_group(0) + kill(-pid)）
                   → 本次调用失败（错误文本：「超过 N ms 没有回话」）
                   → 下一次触发 ensure_child() 重新 spawn、等 ready、重放声明
```

| 项 | 值 |
|---|---|
| 单次调用预算 | 任务/路由的 `budget_ms`，否则 `EXEC_BUDGET_MS`（2000ms） |
| IPC 宽限 | **+250ms**（预算 2s 的插件不该因为几毫秒调度抖动被杀） |
| 加载预算 | `LOAD_BUDGET_MS`（默认 10s），超时同样杀进程组 |
| 被杀之后 | 任务算失败 → 交给熔断器；插件**内存状态丢失** |
| 重启 | 下一次 `invoke` / `tick` 自动拉起；注册声明还在调度器里，不重复安装 |
| 卸载 / 热更新 / 惰性回收 | 主动 kill；下次触发再拉起 |

**和 QuickJS 的语义差别必须认**：QuickJS 超预算时插件状态还在（异常打断后下一个任务继续用
同一个 `Context`）；外部插件被杀之后状态清零。所以外部插件要把跨调用状态落到数据目录 /
SQLite，不能只放模块变量。见 [ext-runtime-protocol.md §8](ext-runtime-protocol.md#8-超时杀进程重启)。

### 7.3 执行预算还不够：任务熔断

执行预算保住了引擎，但**保不住 CPU** —— 一个 `while(true){}` 的任务每轮都会烧满整个预算，
变成「引擎活着，但盒子一直在满负荷」。

```text
   连续失败 N 次 ──> 熔断，冷却 base 时长
                      │
                      ├─ 冷却结束 ──> 半开：放行一次
                      │                 ├─ 成功 ──> 完全恢复（退避计数清零）
                      │                 └─ 失败 ──> 再次熔断，冷却 ×2（上限 max）
                      └─ 期间不执行
```

熔断期间把 `next_fire` 直接钉在「冷却结束时刻」，所以既不会漏掉重试，也不会在冷却期内空转。

**实测（预算 500ms / 阈值 3 / 首次冷却 5s，QuickJS 死循环）**：

```
19:15:25/26/27  连续失败 3 次
19:15:27        熔断（第 1 次），冷却至 19:15:31.566      ← 5s
19:15:32        半开重试失败 → 熔断（第 2 次），next=19:15:41.566  ← 10s（退避）

CPU 占用（进程 CPU 时间差值法）：
  阶段A 熔断前（死循环全速跑）: 4s 内 +1.50s → 37.5%
  阶段B 熔断后（冷却中）:      8s 内 +0.01s →  0.1%   ← 降两个数量级
  对照组 alive: runs=28，全程不受影响
```

面板上会显示 `已熔断 ×N` 与冷却剩余时间（`next_run` 即重试时刻）。

**完整生命周期实测**（`examples/recovery-plugins/flaky.js`：前 3 次故意失败，之后正常）：

```
19:17:14/15/16  失败 3 次
19:17:16        熔断（第 1 次），冷却至 19:17:19.269    ← 3s
19:17:19        半开重试成功，已恢复调度                 ← trips 清零、连败清零
19:17:20/25     flaky 已恢复正常，第 5 / 10 次触发
```

**外部插件的熔断是同一条路**：超时杀进程 → 调用失败 → 连续 N 次熔断。区别是每次失败
多付一次「重新 spawn + ready」的代价（Node 约几十到几百毫秒）。

### 7.4 惰性回收：外部子进程是真的会退出

`PLUGIN_LAZY=1`（默认）时，没有路由、没有 `on_tick`、没有开着的 WS、且下次触发还在
`PLUGIN_IDLE_EVICT_MS` 之外的插件会被卸出内存：

- **QuickJS**：释放 `Context` / `Runtime`。省的是 JS 堆，**RSS 基本不动**
  （实测见 [lazy-plugins.md](lazy-plugins.md)）。
- **外部 Node/Bun**：直接杀子进程。**RSS 是真的会掉**（Node 40–80 MB 量级），
  代价是下次触发要重新启动解释器 + 重新加载插件。

触发前 `PLUGIN_PRELOAD_MS`（默认 20s）会把它装回来；面板上点「立即执行」会先装回。
外部插件的「装回」= spawn + 等 `ready`，所以更慢，`PLUGIN_PRELOAD_MS` 的意义也更大。

### 7.5 ⚠️ 运维约束：一个 DB 只能被一个实例使用

`sync_jobs` 在启动时会清理「插件代码 / 任务目录里没有声明」的任务，所以**两个实例共用一个
`data/panel.db` 会互相覆盖 jobs 表**。外部插件/脚本也拿到了 `PANEL_DB` 路径 ——
**不要让它们写面板的表**（`jobs` / `runs` / `plugin_state`），那等于绕过锁改权威状态。
多实例部署时每个实例要用独立的 `DB_PATH`（以及独立的 `BIND_ADDR`）。

### 7.6 🟡 P1：两套调度机制并存

第一轮的 `on_tick`（宿主 `tokio::time::interval` 每秒驱动）和第二轮的 cron 是两套独立机制。
`on_tick` 现在只是第一轮的历史包袱，合理做法是把它收敛成一个内置的 cron 任务。

### 7.7 🟡 P1：任务串行执行

同一条 worker 上所有到期任务依次执行。跳拍机制保证不会积压，但一个慢任务会推迟同
worker 的其他任务。外部插件虽然把计算放进独立进程，**一次 `invoke` 仍会占住一条 worker
直到返回**；要彻底隔离得让调度与执行解耦。

脚本任务另有一条 script worker（默认最后一条）：一个长脚本会占住它整个运行期，
推迟同一条 worker 上的后续脚本 —— v1 没有独立脚本池，见 [script-jobs.md §10](script-jobs.md#10-已知限制v1)。

### 7.8 🟢 P2：其余

- **`jobs` 只有计数 + 最近错误**：执行历史在 `runs` 表，但没有按插件的聚合视图
- **数据库单锁**：`tasks` 心跳、`jobs` 状态、HTTP 读、外部插件 RPC 共用一个 `Mutex<Connection>`
- **时区依赖 `Local`**：盒子 TZ 配错则 cron 全错，应支持显式时区配置
- **DST 未测试**：`.earliest()` 只是兜底，没有跨夏令时的用例
